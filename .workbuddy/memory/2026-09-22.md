## 三个关键设计决策（值得写进博客/面试）

### 1. 注册会一并创建个人租户

`refresh_tokens` 是租户级表（`tenant_id NOT NULL`，受租户过滤保护）。
若注册只建用户，该用户就处于「无租户 → 签不出 refresh token」的死局，
而让他加入租户需要邀请流（阶段 5+）。

所以**自助注册 = 开一个团队**（Slack / 飞书形态）。
平台管理员补开租户的路径保留，两者共用 `provision_default_roles`。

### 2. repository 必须按「表是否带 tenant_id」分两个基类

`User` / `Tenant` / `Permission` 是全局表。登录发生在**还没有租户上下文**的时刻——
上下文要靠 access token 才能设，而 token 正是登录要签发的产物，**循环依赖**。
给这条查询套租户守卫，登录会永远失败。

拆基类是**动隔离地基**的操作，所以配了 `tests/security/test_repository_guard.py`
钉死两件事：全局表确实可无上下文访问；租户表**仍然**拒绝。
第二条更重要——它坏了不报错，只会某天被发现跨租户泄露。

### 3. 登录时「我属于哪些租户」是受控的例外

`TenantMemberRepository.list_memberships_for_user()` 用 `raw_select()` 绕过守卫。
安全论证：过滤键 `user_id` 来自**已验证的凭据**（密码校验通过的用户 / 验签通过的 token），
调用方只能枚举**自己**的成员关系；返回行不含任何租户业务数据。
与 `bypass_*` 的区别是后者关掉整个作用域的过滤，用于平台运营。

> 另外：刷新/登出**不需要**绕过守卫——refresh JWT 自身带 `tenant_id` 且经验签，
> 流程是「先验签 → 用声明设上下文 → 再走受守卫查询」。顺序不能反。

## 踩到的两个坑（都是「测试绿但真实运行有问题」）

### 坑 1：coverage 严重低报 —— 必须配 greenlet 并发

**这是今天最有价值的发现。**

现象：`auth_service.py` 覆盖率 47%，可我跑了 25 个认证用例，断言了 201/200。
用 AST 逐函数统计后发现规律：

```
  async register      covered   3/ 67     ← 只有 def 那一行
  async login         covered   2/ 61
  async refresh       covered   7/ 79
  sync  _slugify      covered   5/ 11
```

**每个 `async def` 只统计到函数签名，函数体全部算未覆盖。**

根因：SQLAlchemy 的 async 引擎内部用 **greenlet** 把同步驱动桥接成异步。
代码一旦 `await session.execute(...)`，执行流切进 greenlet，而 coverage
默认只按 thread 跟踪执行上下文——切出去之后同一个协程函数里的后续行不再被记录。

修法：`[tool.coverage.run]` 加一行

```toml
concurrency = ["greenlet", "thread"]
```

效果：`auth_service` **47% → 85%**，整体 **82% → 90%**。

**教训：这个项目此前的覆盖率数字一直是低报的**（第 1 周报的 84% 也是）。
配置缺这一行时，所有 async 业务代码的覆盖率都不可信，
而且低报方式极具迷惑性——测试明明断言了返回值，报告却说没跑过。
`tests/` 覆盖率门禁在这种状态下是失真的。

### 坑 2：内存库没有表 —— 又一次「测试绿 ≠ 能启动」

真实起 `uvicorn` 跑注册，**500**：`sqlite3.OperationalError: no such table: users`。

根因：零依赖模式用 SQLite **内存库**，内存库随进程生灭；
而 `alembic upgrade head` 是**另一个进程**，迁移的是一个独立的空内存库——
对服务进程看到的库毫无影响。测试里 `conftest.py` 自己 `create_all` 了，CI 也是，
所以**测试和 CI 全绿，只有真起服务才暴露**。

修法：`app/main.py` 的 lifespan 里加 `_bootstrap_local_schema()`，
仅在「`local`/`test` + SQLite 内存库」时 `create_all` 并打警告。
持久化数据库仍必须走 Alembic，否则本地与线上漂移。

> 这已经是第二次同类问题了（第 1 次是 `DATABASE_URL` 同步驱动）。
> **规律：凡是「测试与 CI 自己额外做了一步准备」的路径，都要专门用真实启动验证一遍。**
> `conftest.py` 建表、CI 设 `DATABASE_URL`——这两个都是「掩护坏默认值的脚手架」。

## 其他改动

- **`bypass_context` 修 bug**：原本退出时硬编码 `set_context(tenant_id=None)`，
  嵌套调用会**静默抹掉外层租户上下文**（退出后隔离就没了，且无日志）。
  改为 snapshot + restore，语义变成「借用一下，用完还回去」。已配异常路径的测试。
- **`bypass` 下写租户表必须显式传 `tenant_id`**：守卫在 bypass 下返回 0，
  不拦就会写入 `tenant_id=0`，违反外键且报错指不到真实原因。
- **JWT 密钥长度守卫**：PyJWT 对 18 字节的 dev 占位密钥发 `InsecureKeyLengthWarning`
  （RFC 7518 §3.2 要求 ≥32 字节）。原来只校验「不等于默认值」，
  设成 `JWT_SECRET=abc` 也能过。现在 staging/prod 下同时卡长度。
- **`token_type="Bearer"` 的 S105/S106 误判**：用行级 `# noqa` 而非整文件忽略——
  `auth_service.py` 是核心认证文件，不该为一行放开关掉整文件的硬编码口令检测。
- **复用检测的语义细分**：只有 `revoked_reason == "ROTATED"` 才算复用并拉响警报。
  `LOGOUT` / `EXPIRED` 只是废票，普通 401 即可——否则每次「登出后再试一次」
  都触发全量撤销 + warning，告警疲劳会让真泄露淹没在噪音里。

### 顺带处理的两件事

1. **`.gitattributes` 强制 LF。** 初始化前实测仓库混有 20 个 CRLF 文件
   （整个 `alembic/` 目录 + `alembic.ini` + `script.py.mako`）与 76 个 LF 文件。
   混合行尾会让 `git diff` 出现「整文件改动」的假象，也会让本地与 Linux CI 的
   格式检查结果不一致。加 `* text=auto eol=lf` 后，提交对象里已全部是 LF。
2. **`.venv` 未泄漏。** 78 个受控文件，`.venv` / 各类缓存 / `.env` 均被正确忽略。
   已实测确认（`git ls-files | grep -c '^\.venv/'` = 0）。
