|---|---|

**最重要的一条结论不是数字，而是：**

> 这次压测抓到了 **431 项测试全部通过**之后仍然存在的两个并发缺陷。
> 它们在功能测试里**永远不会暴露**——因为功能测试是单线程串行的，
> 而两个 bug 都只在「同一时刻有多个请求」时出现。

## 二、测试环境（★ 先看这个再看数字）

| 项 | 值 | 说明 |
|---|---|---|
| 数据库 | **SQLite 文件库**（`sqlite+aiosqlite:///./_bench.db`） | **不是生产配置**。生产用 PostgreSQL |
| 建库方式 | `alembic upgrade head` | 用迁移产物，与 compose 的 api 服务同路径 |
| Redis | **fakeredis**（进程内） | 零依赖降级模式，无真实 Redis |
| 服务 | 单进程 `uvicorn`，**未开 `--workers`** | ★ 单进程！这是数据偏低的主因 |

| 限流配额 | 临时放大到 1000 万/分钟 | 否则测的是「限流是否生效」，不是「能承载多少」 |

★ **这台机器上没有 Docker，也没有 PostgreSQL**，所以这份报告**不能**用来推断生产容量。
它能回答的是「代码在并发下有没有 bug」——而这个问题它回答得非常干净。

## 三、方法与口径

三个场景，都走**真实业务链路**（不是只打 `/health`）：

| 场景 | 路径 | 覆盖的中间件/依赖 |
|---|---|---|
| 最轻路径 | `GET /health` | CORS → RequestID → **Metrics** → 路由（不碰 DB、不鉴权） |
| 列表查询 | `GET /api/v1/projects` | 全链路：鉴权 → 租户隔离钩子 → DB → **限流** → **指标采集** |
| 混合读写 | 80% 列表读 + 20% 建项目写 | 上面全部 + INSERT + 审计落库 + 唯一约束 |

口径说明（避免误读）：

- **延迟是端到端的**（含客户端与事件循环开销），所以略高于服务端
  `http_request_duration_seconds` 指标。它是「用户体感」，不是纯服务端处理时间。
- **分位数用最近秩法**（nearest-rank），样本少时比线性插值稳。
- 并发靠 asyncio 协程，**不是**多线程/多进程——测的是「单进程 async 的 I/O 并发能力」。

## 四、★ 压测抓到的两个真实缺陷

### 缺陷 1：`StaticPool` 被误用到文件库 → 8%~14% 的请求直接 500

**现象**：混合读写场景错误率 14.37%（20 并发）/ 8.38%（50 并发），日志里 135 次：

```
sqlite3.OperationalError: cannot commit transaction - SQL statements in progress
```

**根因**：`app/core/db/session.py` 里原本是

```python
if _is_sqlite:                      # ← 所有 SQLite，包括**文件库**
    _engine_kwargs["poolclass"] = StaticPool
```

`StaticPool` 的语义是「**所有会话共用同一条连接**」。而原来那句注释的理由
（"否则每个连接一个空库"）**只对内存库成立**。

文件库套上 StaticPool 之后，所有并发请求挤在同一条 SQLite 连接上——
一个请求正在连接上执行语句时，另一个请求的 commit 就会撞上它。

**为什么 431 项测试没抓到**：功能测试是单线程串行的，永远不会有
「语句正在进行中」这���状态。**这个 bug 只能在并发下复现。**

**修复**：`StaticPool` 只给内存库用，文件库改走默认池；并给 SQLite 加
`timeout=30`（SQLite 同时只允许一个写者，锁竞争时排队而不是立刻失败）。

### 缺陷 2：`except` 里的清理动作自己会抛异常 → 「降级」变成 500

**现象**：修好缺陷 1 之后，混合场景仍有 8%~10% 的 500，日志里有 77 次
`unhandled_exception`。

**根因**：`audit_service.record()` 声明了「任何失败都降级，绝不抛异常」，但实现是：

```python
except Exception:
    await session.rollback()        # ← 连接已坏时，这一行自己会抛
    logger.exception("audit_write_failed", ...)
```

连接已经不可用时（例如上面那个 SQLite 错误之后），**`rollback()` 本身也会失败**，
而这个新异常从 `except` 块里逃了出去 → 接口 500。

**这违背了函数自己的承诺**：写一条审计失败，不该让整个业务请求失败。

同一模式在 4 处出现（审计、通知、附件、注册冲突），都会：
1. 让「吞异常」的路径变成 500；或
2. 让本该抛 `ConflictError`(409) 的路径被替换成 500 —— 用户看到的状态码变了。

**修复**：抽出 `safe_rollback()`，清理失败只记日志；并把顺序倒过来——
**先 `logger.exception` 记原始异常，再做清理**（反过来的话日志里只剩清理失败，
真正的原因反而丢了）。

### 修复前后对比

| 场景（20 并发混合读写） | 修复前 | 修复后 |
|---|---|---|
| 错误率 | **14.37%** | **0.00%** |
| 状态码分布 | `{'200': 605, '500': 73, '<exception>': 42, '201': 80}` | `{'200': 640, '201': 160}` |
| 服务端未处理异常 | 多次 | **0** |

## 六、瓶颈分析

### ① 并发从 20 提到 50，QPS 不升反降 —— 瓶颈不在并发度

`/health` 在 20 并发时 250.9 QPS，到 50 并发反而只有 119.3。

原因：**服务是单进程**。请求在事件循环里排队，并发只让「排队长度」变长，
不增加每秒处理量。这也解释了为什么 p95 从 179 ms 跳到 1269 ms。

> 结论：这份数据的天花板是**单进程处理能力**，不是 SQLite、不是应用代码。
> 要横向扩展得先起多个进程（`uvicorn --workers N` 或多实例 + 负载均衡），
> 而本机跑不了多进程压测（压测端自己也是单进程，会先成为瓶颈）。

### ② 混合读写是真正的瓶颈（QPS 掉到 55.8）

纯读 156.7 QPS，混入 20% 写之后掉到 55.8 —— **掉了一倍多**，而写只占 20%。

原因链条：INSERT → 审计 INSERT → 两笔事务提交，而 **SQLite 同一时刻只允许一个写者**。
写操作互相排队，`timeout=30` 让它们「等」而不是「失败」，但等待直接体现在 p99 上
（20 并发 2.4 秒、50 并发 3.6 秒）。

> 结论：**这正是 SQLite 降级模式的预期代价**。
> 生产用 PostgreSQL（多版本并发控制 MVCC）不会有这个限制。
> 零依赖模式换来的是「跑得起来」，代价就是并发写能力——这是自觉的取舍，不是缺陷。

### ③ 轻路径 61 ms 的 p50 偏高

`/health` 不碰数据库，p50 却有 61 ms。这主要是**压测端自身**的开销：
单进程 asyncio 要同时发 20 个请求、序列化、发包、收包、解包，
排队时间被计入了每个请求的延迟。

> 所以这组延迟应读作「**端到端体感**」，不是服务端处理时间。
> 服务端真实处理时间请看 `/metrics` 里的 `http_request_duration_seconds`。

## 七、这份报告**不能**用来做什么

必须写清楚，避免误用：

- ❌ **不能推断生产容量**——数据库是 SQLite、生产是 PostgreSQL
- ❌ **不能推断多实例表现**——服务与压测端都是单进程
- ❌ **不能推断索引效率**——数据集只有 20 行，索引几乎不会被命中到缓存之外
- ❌ **不能推断真实网络条件**——全部走 loopback，无 RTT
- ✅ **能回答**：「代码在并发下有没有 bug」——而这一点它回答得非常干净（抓到 2 个）

要得到能推断生产的数字，最少需要：PostgreSQL + 多实例服务 + 独立压测机
（k6/Locust）+ 万级数据集。

## 八、怎么复现

```bash
# ① 用迁移建库（与 compose 的 api 服务同一条路径）
DATABASE_URL="sqlite+aiosqlite:///./_bench.db" APP_ENV=test \
  python -m alembic upgrade head

# ② 起服务（压测模式：配额放大，否则测的是限流而非容量）
DATABASE_URL="sqlite+aiosqlite:///./_bench.db" APP_ENV=local \
USE_FAKEREDIS=true CELERY_ALWAYS_EAGER=true \
RATE_LIMIT_PER_MINUTE=10000000 \
  python -m uvicorn app.main:app --port 8000

# ③ 另开一个终端跑压测
python -m scripts.loadtest --concurrency 20 --total 800 --json docs/b10_c20.json
python -m scripts.loadtest --concurrency 50 --total 800 --json docs/b10_c50.json
```

★ 脚本用 `httpx` + `asyncio` **自写**，没有引入 locust——
理由与口径说明见 `scripts/loadtest.py` 的模块 docstring。
