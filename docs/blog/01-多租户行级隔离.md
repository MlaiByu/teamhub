# 多租户行级隔离：实现与四个坑

> 项目：TeamHub（多租户团队协作平台）。技术栈 FastAPI + SQLAlchemy 2.0 async + PostgreSQL。
> 本文讲**机制**与**踩坑**，不讲功能清单。

多租户的隔离方案有三档：独立库、独立 schema、共享库加行级过滤。

前两档隔离得最彻底——隔离的代码在物理上就不可能出错。代价是**运维与连接数爆炸**：
一万个租户就是一万个库，或者至少一万个 schema。SaaS 场景下我选了第三档：
**共享库、共享 schema、所有业务表带 `tenant_id`**。

选择它的代价是：**隔离从「结构保证」退化成「代码保证」**。而代码保证意味着——
**你写的每一行忘记带 `tenant_id` 的代码，都是一个越权漏洞**。

这篇文章讲怎么把「代码保证」尽可能变成「结构保证」，以及我踩的四个坑。

---

## 方案：Mixin + 钩子自动注入

核心思路：**不让业务代码写 `where tenant_id = ?`，而是让 ORM 在编译 SQL 时自动加上**。

```python
class TenantScopedMixin:
    tenant_id: Mapped[int] = mapped_column(ForeignKey("tenants.id"), nullable=False)
    tenant_id = declared_attr(deferred_column())


def install_tenant_hook(engine):
    @event.listens_for(engine.sync_engine, "do_orm_execute")
    def _inject(execute_state):
        tenant_id = current_tenant_id.get()
        if tenant_id is None:
            return
        for entity in execute_state.compile_state().entities:
            if issubclass(entity.entity, TenantScopedMixin):
                criteria[entity.entity] = entity.entity.tenant_id == tenant_id
        execute_state.statement = execute_state.statement.options(
            with_loader_criteria(TenantScopedMixin, criteria)
        )
```

业务代码写 `select(Project)`，出来的 SQL 自动带 `WHERE projects.tenant_id = ?`。

这样想「忘记加 tenant_id」就不可能了——**因为业务代码里根本没写这条过滤**。

## 坑 1：语义没定义清楚，过滤会「过头」

第一版我给数据范围（owner/dept 可见性）写了这样的代码：

```python
scope = current_data_scope.get()   # 没设置时返回默认值 SELF
user_id = current_user_id.get()    # 没设置时返回 None
criteria = {cls.owner_id == user_id if scope == DataScope.SELF ...}
```

于是空上下文时：`scope = SELF`、`user_id = None` →
钩子注入 `owner_id IS NULL` → **SQL 里 NULL 比较恒为假** → **一条数据都查不到**。

这个 bug 极其隐蔽，因为**我设计的验收标准前四条全都通过了**：

| 验收项 | 结果 |
|---|---|
| 用 A 的上下文查列表，只返回 A 的数据 | ✅ |
| 用 B 的 id 查 A 的数据，返回 None | ✅ |
| 插入时自动补 tenant_id | ✅ |
| 写入不属于自己的数据被拒 | ✅ |

直到第 5 条才暴露：

| 验收项 | 期望 | 实际 |
|---|---|---|
| 清空上下文后应能看到全部租户的数据 | 2 条 | **0 条** |

**真相是：钩子从来就没有「不过滤」过。它只是过滤得太严，恰好让前四条也成立。**

> **这是隔离测试里最反直觉的一点：反向验证不是「锦上添花」，
> 它是唯一能区分「过滤正确」和「过滤过头」的断言。**

「看不到别人的数据」这条断言，在「谁都看不到数据」时**同样成立**。
只有「能看到自己的数据」和「能看到别人的数据（在 bypass 模式下）」两条一起，
才构成完整证明。

修法有两处，缺一不可：

```python
# 1) 把语义写死：完全空上下文 ⇒ 不注入任何条件
def _is_empty(ctx):
    return ctx.tenant_id is None and ctx.user_id is None and ctx.dept_id is None

# 2) 把「不许静默全量」这条防线从钩子挪到 repository 入口
def require_tenant_context():
    if is_bypass():
        return 0
    if current_tenant_id.get() is None:
        raise TenantContextMissingError(...)
```

第 2 点是关键：**钩子是「自动补过滤」，它没法拒绝调用**。
真正能「fail fast」的是 repository 层——它能抛异常。

> 教训：**「自动补上」和「拒绝执行」是两种不同的保护，别指望一个机制干两件事。**

## 坑 2：Mixin 上声明的列，在 Mixin 层碰不到

钩子需要拿 `TenantScopedMixin.tenant_id` 来构造条件。第一版直接写：

```python
criteria[TenantScopedMixin] = TenantScopedMixin.tenant_id == tenant_id
# ❌ 启动即炸：Cannot compile Column object until its 'name' is assigned
```

原因是 `declared_attr` 声明的是**模板**，不是列。
只有当某个实体类继承了这个 Mixin，SQLAlchemy 才会生成真正的 `Column` 并绑定名字。
在 Mixin 类本身上访问 `.tenant_id`，拿到的是一个未绑定的占位对象。

修法是把求值推迟到 SQLAlchemy 把实体类交回来的时候——
`with_loader_criteria` 本来就支持传 callable，正是为这种场景设计的：

```python
criteria[TenantScopedMixin] = lambda cls: cls.tenant_id == tenant_id
```

> 教训：**`declared_attr` 是「生成规则」，不是「列」。**
> 想在 Mixin 上写通用逻辑，就必须接受「拿到实体类之后才能碰列」这个约束。

## 坑 3：钩子只管 SELECT，批量写完全绕过它

这是四个坑里**最危险**的一个——它不是「没生效」，而是「看起来生效了」。

项目里的约定一直是：

> 业务代码不手写 `tenant_id`，钩子会注入。

这句话对 **SELECT** 完全成立。我也是在压测阶段才发现它对 **UPDATE / DELETE 不成立**。

当时的日志长这样：

```
sqlite3.OperationalError: cannot commit transaction - SQL statements in progress
```

追下去发现根因是一行配置错误（StaticPool 误用到文件库，所有并发请求共用一条连接），
但修完之后仍有 500。继续查才挖到真正的隔离问题：

```python
# 修复前的 revoke_chain（登出时撤销该用户的全部 refresh token）
stmt = (
    update(RefreshToken)
    .where(
        RefreshToken.user_id == user_id,      # ← 只有 user_id，没有 tenant_id
        RefreshToken.revoked.is_(False),
    )
    .values(revoked=True)
)
await session.execute(stmt)                     # 钩子**完全不介入**
```

`with_loader_criteria` 是** loader option**，它的作用对象是「ORM 实体加载」。
`session.execute(update(...))` 走的是 Core，压根不经过实体加载——**钩子连触发的机会都没有**。

我单独验证了这一点：

```python
# 在租户 1 的上下文里执行一条不带 tenant_id 条件的 DELETE
await session.execute(delete(RefreshToken).where(RefreshToken.revoked.is_(False)))
# 结果：两个租户的行一起被删了
```

修复的方式**不是**「逐处记得手写 `tenant_id`」——那等于从「结构保证」退回「自觉保证」，
而且下次 review 漏掉一处又是漏洞。正确做法是**把约束做进基类**：

```python
class TenantAwareRepository(BaseRepository):
    async def bulk_update(self, values, *conditions) -> int:
        stmt = update(self.model).where(self._tenant_condition(), *conditions).values(**values)
        ...

    def _tenant_condition(self):
        return self.model.tenant_id == self.require_tenant_context()
```

于是「写批量 UPDATE」这件事**只能通过带租户条件的封装发生**，
裸 `update()` 变成一个不该出现的写法。

> 教训：**「钩子会自动处理」这种约定一定有它的适用范围，
> 而这个范围往往比你以为的窄。**
> 凡是「框架帮不上忙」的地方（批量写、缓存、消息队列），
> 隔离就得**换一个机制重新做一遍**，而且要让它同样无法漏写。

同一个项目里，隔离一共做了三遍，因为它们互相不覆盖：

| 隔离面 | 机制 | 漏了的后果 |
|---|---|---|
| 数据库行 | `tenant_id` 钩子 + repository 守卫 | 看到别家公司数据 |
| 缓存 key | `cache_key()` 强制带租户前缀 | **读到别人的缓存**（且不报错） |
| 限流 key | `build_key()` 强制带租户前缀 | **一个租户吃光全平台配额** |

缓存那一条尤其值得说：**数据库至少有 `NOT NULL` 约束和查询钩子兜底，
而缓存就是个裸 KV——key 写错了不会抛任何异常**，只会静默返回别人的数据。

## 坑 4：测试怎么写，决定你能不能抓到越权

前三个坑都是「实现」层面的。第四个是**方法论**层面的，它决定了你会不会发现前三个。

我的隔离测试一开始是**逐接口写**的：测 `GET /projects` 的隔离、测 `POST /tasks` 的隔离……
写了 20 多个用例，全绿。

然后我把它重写成了**矩阵**：

| 身份 | 数据范围 | 应看到的资源数 |
|---|---|---|
| 管理员 | ALL | 4 |
| 部门经理 | DEPT（本部门） | 2 |
| 成员 A | SELF（且自己是 owner） | 1 |
| 成员 B | SELF（但那些不是自己的） | 0 |

断言方式是「**列表返回集合精确等于期望集合**」——多一条是泄露，少一条是误杀。
对每个身份 × 每类资源 × 每组接口（列表/详情/更新/删除/评论/附件）都跑一遍。

改写之后**第一轮跑就抓到 9 个失败，全部集中在附件**：

```python
# 修复前的 list_attachments
async def list_attachments(session, *, biz_type=None, biz_id=None, user_id):
    return await AttachmentRepository(session).list_for_biz(biz_type, biz_id)
```

`Attachment` 表**不带**数据范围 Mixin，而这里也没有任何「挂靠实体可见性」的校验。
后果有三条：

1. 带 `biz_id=<别人的项目>` → 能列出同租户别人项目的附件
2. **不带参数** → 列出**全租户**所有附件
3. 知道 `attachment_id` 就能下载任何同租户附件

第 2 条是最容易漏的：**带参数时人会想着去校验，不带参数反而直接全表扫。**

> 漏掉这一步的原因不是「不会写隔离」，而是**我从来没把附件当成一种
> 「挂靠在别人身上的数据」**。它自己没有 owner_id，但它有 parent。

修复时我拒绝了一个看起来更简单的方案：给 `Attachment` 也加数据范围 Mixin。
因为那样会把语义变成「上传者自己的范围」——但真实语义是
「**这个附件挂着的那个实体，调用方能不能看到**」。
A 上传附件到 B 负责的任务，B 应该能看到；按上传者过滤就完全错了。

> 教训：**逐接口测试问的是「这个接口对不对」，
> 矩阵测试问的是「同一个接口换个身份还对不对」。后者才是越权的检测方式。**
>
> 更一般的说法：当你发现自己在为每个接口写相似的隔离断言时，
> 说明你缺的不是断言，是**一个能让组合爆炸自动展开的测试结构**。

## 收尾：几条可复用的判据

这四条踩坑之后，我给自己留了几条判据：

1. **隔离断言必须成对**：正向（只看到自己的）+ 反向（清空上下文看到全部）。
   没有反向验证的隔离断言，等于没有断言。

2. **凡「框架自动补的」，都要确认它的边界**。查一次文档不够，
   要**写个最小验证跑一遍**——`with_loader_criteria` 对 bulk 写不生效，
   就是这么确认的。

3. **框架覆盖不到的地方，隔离要重做一遍**，并且用封装让它无法漏写。

4. **判据要能回答「结果被什么约束住了」**。
   判据：每个 list 方法都要能回答「它的结果被什么约束住了」。
   答不上来的那个方法就是没被保护的那个。

最后一条我的个人体会：**多租户隔离的难点不在技术，在「确认它一直有效」**。
写出来只要一天，而我在第 6 周和第 10 周各被它教育了一次——
一次是测试方式不对，一次是并发场景下的批量写。
